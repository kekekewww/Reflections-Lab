# ADR-012: Codex Orchestration, Muse Priority, and Safe Automatic Handoff

> **2026-10-27: The role policy and mandatory Muse-first policy have been superseded by [ADR-013](013-codex-primary-development.md).** The following retains Phase3 history; the Harness is Optional. Independent validation / mutual exclusion / budget principles remain, but cannot serve as prerequisites for current product work.

- Status: Accepted, 2026-10-26; see the [Phase3 report](../../09-agents/PHASE3_REPORT.md) for implementation and test evidence.
- Decision: Preferred Executor=Muse Code, Fallback Executor=Codex, Orchestrator=Codex; Verification Authority=an independent automated runner / domain reference fixed in advance, with an isolated review agent added when needed. Acceptance gaps must remain visible and cannot be replaced by the implementer's own assessment.
- Task authority: `knowledge/tasks/*.json` remains the sole work authority. The Task Contract fixes scope / acceptance / budget. Run state preserves PENDING, ASSIGNED_MUSE, RUNNING_MUSE, MUSE_QUOTA_EXHAUSTED, HANDOFF_PENDING, ASSIGNED_CODEX, RUNNING_CODEX, VERIFYING, REPAIR_REQUIRED, COMPLETED, BLOCKED; the Wiki task's high-level BACKLOG…DONE states are not converted into another competing list. `agent_execution` is a detailed projection with run artifact references.
- State preservation: Continue with the same task_id / milestone_id / goal_id, fixed contract hash, acceptance hash, Git revision / workspace contents and diff, successful checkpoints, remaining work, and model / CLI provenance. Do not reimplement completed items; validation may be rerun for new changes. Preserve hashes of untracked content even without HEAD.
- Failover: Use bounded backoff for recoverable 429 / temporary failures, respecting Retry-After and the time budget; distinguish explicit subscription exhaustion / billing evidence from unknown values. Do not call 401 / 403 quota exhaustion; unknown errors fail closed. First stop dispatch, confirm the original writer has stopped, preserve state, then assign the next executor; if process containment cannot be proven, mark BLOCKED rather than risk overlapping writers.
- Codex adapter: By default, the existing Orchestrator enters Implementation Mode, reads the handoff, modifies the remaining scope, and then submits a completion signal to the runner; the runner validates separately. This signal does not mean validation passed. A separate Codex CLI process requires separate session / sandbox validation; do not assume it can call its own chat.
- Switchback: Muse recovery updates only resource evidence; switch back only when the current task is complete or at a safe checkpoint proven to have no writer. Retain the sticky executor / switching limits; do not switch repeatedly on each quota poll.
- Budget: Separate four dimensions: development subscription, development Meta API, Codex usage, and product Meta runtime; unknown remaining balances are null. Monetary limits default to 0; do not raise limits, change accounts, or automatically buy credits. Manual observations record only their source and time and cannot masquerade as live API queries.
- Product runtime: The model / tool provider remains Meta; explicitly label provenance for mock / recorded responses, and mark live tests BLOCKED / NOT RUN. Changing the coding executor does not change the product model, and Codex output cannot stand in for Meta validation.
- Isolation: When HEAD exists, the operator prepares a worktree; without HEAD, use explicit isolated fixture directories and content snapshots. Do not silently commit / reset to create a worktree. Harness cooperative locks do not isolate malicious processes; an OS sandbox remains necessary.
- Alternatives: Recursively launching its own Codex chat (unverified, not adopted); calling all errors quota (misclassification, not adopted); policy without a runner (does not meet requirements); relaxing failing tests (prohibited).
- Limitations: Actual Muse model output, billable APIs, complete product UI / physics / audio E2E, and remote CI may be marked PASS only after actual execution. A mock runner proves control flow, while CLI echo proves the offline protocol; neither proves model quality or live failover.
