# Browser Threads, Recording, and Performance Research

Status: **research and proposed future design; not an accepted performance guarantee**. Checked: 2026-10-29. Code baseline: `c210ca882ca8503b322c28884bf1e9f6e9fe126d`; subsequent changes require their own actual diff and tests. This report does not change the [formal performance budget](../06-validation/PERFORMANCE_BUDGET.md), [frozen acceptance](../11-v1/ACCEPTANCE.md), or [confirmed amendments](../11-v1/ACCEPTANCE_AMENDMENTS.md). Normal 100% display scaling is the current scope.

## Facts established from the current code

| Path / responsibility | Implementation and evidence | Conclusion and risk |
|---|---|---|
| Application RAF in `src/app/bootstrap.ts` | `frame()` → `created.advance(delta)` → publication flush → next RAF | Runtime scheduling shares the main thread with the view. Independence from React state does not imply a separate thread. Layout, React, view updates, GC, and application work can all delay physics advancement. The GPU can execute in parallel, while draw submission and JS still compete on the main thread. |
| `src/app/runtime.ts:advance` → `PhysicsWorld.advance` | Fixed `1/60 s`; at most four interactive catch-up steps. Interactive overload drops wall time and records it; recording overload pauses and retains ticks. | Fixed dt defines simulation integration time, **not a real-time 60 Hz scheduling guarantee**. Render stalls delay the next advance. Fixed steps do not prove independence from rendering. |

Limits: 32 sources, 256 surfaces/source, 256 paths/batch, 2 MiB payload, 5 s timeout, 128 timing samples. Identity/revision validation and late-reply rejection are present. | The ordinary solver really uses a worker. Single-flight backpressure already exists; an additional unbounded queue is unnecessary. ## Preserve R17 negative evidence

R17 C4 on the [formal performance page](../11-v1/BROWSER_PERFORMANCE.md) provides 600.051 seconds and 19,498 frames of interpretable negative measurements: physics core p95 about 4.8 ms; default/stress worker about 46.3/27.1 ms; observed delivery about 12.4/28.7 ms; renderer-main wall occupancy p95 about 83.23 ms. The original physics/delivery/main targets did not pass. Main wall occupancy is not CPU time; full delivery including unmeasured pre-handler/OS intervals remains UNVERIFIED.

There were also 106.117 seconds of interactive dropped wall time, 1,222 overruns, 1,653 paused advances, recording overload pauses, and final capture/pending failures. Draining outside the window cannot backfill the original 600 seconds. A muted native graph supplies neither actual Worklet deadline/underrun nor human listening evidence. Future quality degradation, device tiers, or cloud candidates must not erase the original FAIL or present a smaller workload as the same acceptance passing.

## Responsibilities and migration order

| Layer | Suitable work to retain / move | Prohibited dependencies and unverified work |
|---|---|---|
| Main thread | UI, Pointer Lock, IME, DOM, Three/R3F view, input commands, bounded pose interpolation, AudioNode control | Avoid large JSON/hash work, full solvers, and long batches. Before physics migration, still measure main-thread fixed steps and per-tick capture separately. |
| Dedicated simulation worker (proposed, unimplemented) | Rapier fixed steps, normalized physics events, Behavior evaluation, tick/revision snapshots. Recording advances tick by tick in bounded batches. | No DOM. Inputs require sequence/tick and cancellable commands. Stable domain IDs stay unchanged; do not pass Rapier handles. OS scheduling can delay workers; a timer is not a real-time clock. |
| Existing acoustic worker | Versioned geometry and source/listener input, bounded-order solver, per-batch budgets | Cache invariant geometry by revision first, then measure transfer improvements. Per-tick recorded evaluation can use an independent lane, separated from interactive latest-pose updates to avoid mutual blocking. |
| Recorder/storage worker (proposed) | Chunk encoding/hashing, IndexedDB/OPFS writes, manifest published last; queue high-water mark pauses producers | Interactive preview may drop wall time; **experiment traces must not lose ticks or overwrite pending frames with latest-only data**. Identify write/quota/cancel failures and crash remnants. Do not publish Captured. |
| Audio render thread / optional Worklet | Existing native graph; only necessary bounded DSP, preallocated buffers, and smoothed parameters in a future Worklet | Never await physics, geometry, network, AI, or storage; no unbounded allocation/logging. Actual profiling must establish whether a Worklet migration helps. |
| Offline render lane (proposed) | Pinned recording → same audio graph or separately verified equivalent DSP → PCM/WAV, separate from interactive runs | Faster-than-real-time behavior requires device measurements. Do not replace the original physics trace or equate outputs from different backends. |

First measure `onTick/capture`, snapshot/encoding, solver compute, request/reply dispatch, AudioEngine consumers, and view updates. Move physics/recorded evaluation where evidence shows benefit; placing another timer on the main thread does not establish decoupling. Recording can use “execute a fixed batch of ticks → await bounded consumers → yield,” retaining run/tick semantics. Interactive view interpolation reads the last complete snapshot and never writes dynamic poses back.

## Transfers, SharedArrayBuffer, and isolation

Current object `postMessage` uses structured cloning. For frequent pose/path updates, one candidate is fixed-layout TypedArrays with a pool of two or three buffers. Transfer ArrayBuffer ownership to the receiver and return buffers after use. Transfer detaches the sender's buffer: never transfer authoritative Scene arrays or arrays still read by the UI. Continue validating metadata, revision, tick, and byte length. Transfer reduces copying of large buffers; it does not eliminate message scheduling or JS validation. [MDN Transferable objects](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Transferable_objects)

Consider SAB only after measurements establish copying/dispatch as a dominant bottleneck. Ordinary pages require a secure context and cross-origin isolation, commonly `Cross-Origin-Opener-Policy: same-origin` plus `Cross-Origin-Embedder-Policy: require-corp` (or a separately verified credentialless approach), and a `crossOriginIsolated` check. Cross-origin WASM, scripts, fonts, audio, and object downloads require appropriate CORS/CORP; OAuth popups and embedded content need separate testing. ADR-010 currently does not require SAB. Adding isolation headers is not a risk-free small change. [MDN SAB](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer), [Google isolation guide](https://web.dev/articles/cross-origin-isolation-guide)

A future SAB design must define single producer/consumer roles, ring size, overflow counters, Atomics publication order, and generation. AudioWorklet must not block waiting for a producer. It may reuse the last complete parameters but must not read partially written frames; absent data requires an explicit hold/fade policy. 128 frames at 48 kHz, about 2.67 ms, is a common benchmark configuration. Read actual array lengths every time; do not assume blocks remain 128 forever. [MDN process](https://developer.mozilla.org/en-US/docs/Web/API/AudioWorkletProcessor/process), [Chrome AudioWorklet patterns](https://developer.chrome.com/blog/audio-worklet-design-pattern)

## Background tabs, disk, and offline RAM

Most browsers pause RAF in background tabs, and pages may freeze or be discarded. Moving work to a worker does not provide a background-completion SLA; service workers do not guarantee arbitrary long computations either. At visibility/freeze boundaries, explicitly pause interactive experiments and checkpoint. Resume at the same tick or report interruption; never turn a background wall-time gap into fictitious simulation data. Optional cloud queues are appropriate for exports that must finish reliably after the page is left. This workflow is not implemented in this round. [MDN RAF](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame), [Chrome Page Lifecycle](https://developer.chrome.com/docs/web-platform/page-lifecycle-api?authuser=2)

Keep small indexes/manifests in IndexedDB. If long traces demonstrably need larger staging, OPFS can store chunks and a worker can use a synchronous access handle. OPFS is origin-private and subject to quotas/clearing policies; **it is not a user-file backup**. Probe space through `navigator.storage.estimate()` and record `persist()` as requested/granted/denied. QuotaExceededError, private mode, site-data clearing, and mid-write shutdown need recovery paths. Write chunks and hashes first, then publish the manifest atomically; reopen only complete hash chains. [MDN OPFS](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system), [Storage quota](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

Minimum offline PCM memory is `durationSeconds × sampleRate × channels × 4 bytes`. At 48 kHz stereo, 30 seconds / 5 minutes / 10 minutes require about 11.52 / 115.2 / 230.4 MB (decimal), excluding decoded assets, AudioNodes, traces, encoding output, copies, and the runtime heap. PCM16 WAV adds `duration × sampleRate × channels × 2 + header` bytes. Keeping complete float PCM and complete WAV simultaneously makes the ten-minute minimum about 345.6 MB, with a higher total peak. OfflineAudioContext produces an in-memory AudioBuffer, not a stream directly to disk. [MDN OfflineAudioContext](https://developer.mozilla.org/en-US/docs/Web/API/OfflineAudioContext)

Long-output candidates are a chunk renderer with overlap/state carry and a streaming encoder. Verify filter/HRTF/IR-tail/delay state across chunks; do not independently render segments and hard-splice them. Start with a short safe local duration and explicit memory headroom, then offer voluntary cloud output. A RAM estimate does not authorize automatic audio uploads.
