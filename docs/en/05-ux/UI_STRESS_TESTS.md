# UI Stress, Failure, and Recovery Acceptance

Updated: 2026-10-26. Status: **Executable test specification; the production UI, browser screenshots, keyboard, screen reader, audio, and user tests are all NOT RUN**. This document supplements the abnormal scenarios in the [component contract](COMPONENT_SPEC.md), [FPS interaction](FPS_INTERACTION_UX.md), and [User Flows](USER_FLOWS.md). `break-ui` provides an approach to inspecting worst-case data; Reflection Lab physics/solver/audio correctness must still be validated against their respective specifications and evidence.

<!-- english-original-anchor --> <a id="執行規則"></a>
## Execution Rules

Use reproducible synthetic fixtures without real personal data, credentials, or commercial sound effects. Record stable scene/object/path/event IDs, revision, seed, counts, hash, and expected rejection or degradation conditions in each fixture. Test rejection of data forbidden by the production domain schema at the import/command boundary; do not first corrupt the runtime and then call the crash acceptable. Inject faults through a test adapter, revalidate the revision after recovery, and do not treat an old job as a successful response.

Apply the current contract boundaries first: the [Scene schema](../../../schemas/scene.schema.json) allows at most 256 objects per scene, and a listener is required and cannot be null; the [AcousticFrame schema](../../../schemas/acoustic-frame.schema.json) allows at most 256 paths per frame; an [AI command label](../../../schemas/ai-tool-request.schema.json) is limited to 160 characters. Use 1000 objects/10000 paths for over-limit rejection tests, or test UI capacity with an **isolated presentation-only adapter**. Do not feed them into the production runtime or call them supported scenes/frames. Scene objects currently have no label field. Persisting names requires a domain decision after authorization of the production feature; this work does not change the schema to accommodate stress tests.

Run individual cases first, then three compound cases: long-name+DPR2+1000 objects, collision storm+solver timeout+Pause, and Holding+IME/modal+lock loss. Each case covers pointer and keyboard alternatives, normal/reduced motion, and the applicable locations in Scene/Simulation/Analysis. At the start of each run, record run/tick, scene revision, selected ID, input owner, recording state, and monitor state; on completion, compare IDs, Undo history, trace, and error state.

## Per-Case Results and Defect Records

For each result, record `caseId`, date, agent/tester, Git revision+dirty diff hash, fixture hash, hardware/browser/device, action steps, expected/actual, PASS/FAIL/NOT RUN/BLOCKED, artifact paths, limitations, issue/task ID, and retest after correction. Annotate screenshots with workspace, viewport, DPR, zoom, motion preference, and state; animations require video or frame-by-frame records, since a single screenshot cannot verify interruption. Restore fixtures after injecting data using upstream `break-ui`; do not save perturbed data as a user scene.

PASS must be limited to the scope of evidence: list static code/document review, snapshots, real-browser keyboard/pointer, real-device audio, physics numerics, acoustic numerics, and performance separately. When browser/visual capabilities are unavailable, save the steps and `NOT RUN`; do not claim visual tests passed. Benchmark metrics use the six separate budgets in [PERFORMANCE_STANDARDS](PERFORMANCE_STANDARDS.md); a plausible-looking UI cannot substitute for finite impulse, obstruction, propagation clocks, A/R/T, or DSP correctness.

When an error is found, first record stable reproduction data and the last valid state, then fix/retest the corresponding case and affected neighboring flows. Cancellation or Retry does not delete original results; mark parts tools cannot capture UNVERIFIED. Update the formal UX specifications for newly discovered product decisions. The Wiki only indexes decisions, reviews, and evidence; it does not maintain another component specification.
